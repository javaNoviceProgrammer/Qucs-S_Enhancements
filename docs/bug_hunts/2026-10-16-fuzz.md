# Bug hunt: fuzzing everything

*16 October 2026 - Qucs-S 27.0.0, `7451b1c` (the Release build and the ASan/UBSan build of it).
13:30 to 15:00, the findings written up as they came. All fixed in the commit that adds this
report.*

The user's request: "let's run a fuzz test on qucs-S. Throw everything you've got at it and see
if it can crash." Every input Qucs-S reads, and every way it can be driven, got a fuzzer. Where
none existed, one was written: four new test functions, a fuzzer of multiphysics models, and a
fuzzer of the tools.

It ran in the foreground on macOS arm64 with ngspice 46. Each run had its own HOME, settings,
cache and trash in a scratch folder. The fuzzers:

## F. Crashes and hangs

### F1. A winding whose core is no core crashes the netlister

Found by the schematic fuzzer (finding `4a354602dc`, from `MagneticCores/core_test.sch`). A
mutant had a part named `N87_1` that was not the core. UBSan, then ASan:

```
magnetics/winding.cpp:115:51: runtime error: member access within null pointer of type 'Property'
SUMMARY: AddressSanitizer: SEGV qarraydatapointer.h:39 in QArrayDataPointer<char16_t>::QArrayDataPointer(...)
```

`Winding::spice_netlist` looks for the part named as its core, and reads its `BHprobes` property.
A part of that name that is no core has no such property: the null pointer was read. A user
reaches it by renaming a resistor to the core's name, or deleting the core and placing another
part under its name.

**Fixed.** A part of that name without `BHprobes` is passed over. Test: `test_erc
aWindingsCoreThatIsNoCore` (W1's core renamed to `R1`: the netlist is written, W1 alone,
W2 keeps its core's nodes).

### F2. A very large image in Markdown takes seconds a frame

Found by the Markdown fuzzer: three documents took 4.3 s, 8.6 s and 17 s to draw once. Each
had `<img src="tall.png" width="20000">`, a picture 1 pixel wide and 20000 tall. Fitted to a
392-pixel page, it is 7.8 million pixels tall. `SmoothImages` (0231545) scaled the whole
image to its drawn size, then drew the part seen: billions of pixels at a pixel ratio of 3.

**Fixed.** Above 16 million device pixels, the image is drawn by Qt's own handler with its
smooth transform, which draws only what is seen. Below that, as before. Test: `test_markdown_doc
imagesAreDrawnSmoothly` (the thin picture at width 20000: drawn in under 1 s, its pixels
right). Broken on purpose: 4225 ms, caught.

### F3. A Lumerical MQW project without a material's parameters crashes the import

Found by the Lumerical fuzzer (`.ldev`, bytes of "zincblende parameters" overwritten). The
import read `kp->child("zincblende parameters")`, an empty `std::optional`, through `->`.
That reads whatever is there: it crashed 4 of 10 runs, and gave garbage the rest.

**Fixed.** A material without its zincblende or wurtzite record is refused: "its material
InGaAs (sample) has no zincblende parameters read". The same check guards its k·p record. That
one cannot be missing today (a material is listed only with it), so it is a guard, not a fix.
Test: `test_fem_lumerical damagedInputsAreRefused` (one record renamed in each of three
projects, five times each). Broken on purpose: a crash (signal 11).

### F4. The Lumerical script reader casts numbers out of an int's range

Found by the Lumerical fuzzer, under UBSan:

```
fem_lumerical_script.cpp:1024:50: runtime error: 2.14748e+09 is outside the range of representable values of type 'int'
fem_lumerical_script.cpp:858:31: runtime error: 2.1e+10 is outside the range of representable values of type 'int'
```

`linspace(0, 1, 2147483648)` and a cell index of `2.1e10`. Each was cast with `int(x)` and
checked after. A cast out of range is undefined: on arm64 it saturates, so the check after
refused it, but nothing promises that. Found on the way, reading: `reshape` multiplied its
sizes as `size_t`, cast from doubles. A size of 2^64 is undefined. Sizes of 2^32 by 2^32 wrap
to 0, and other sizes could wrap round to the values' own count, so the reshape would pass.

**Fixed.** `whole()` makes a number an int: NaN and anything below the range go to INT_MIN,
anything above to INT_MAX, and the checks after refuse them. It is used for indexes, cells,
`linspace`, `zeros`, `ones`, `cell` and `mesh order`. `reshape` takes whole sizes from 0 to
1e7 and multiplies them as doubles. Test: `damagedInputsAreRefused`, eleven hostile scripts,
each refused with its reason (`reshape([1, 2], [18446744073709551616, 0])`,
`[4294967296, 4294967296]`, `[0.5, 4]` among them), and one reshape that works. Broken on
purpose:
- `whole` a cast again: UBSan abort, under the sanitizers;
- the reshape check removed: "reshape: 2 values are not 0" instead of the size's reason.

### F5. Closing a model while it searches for modes waits for the whole solve

Found by the models' fuzzer. All 13 of its findings were `close_document` past its 120-s limit,
right after a `fem_solve` stopped waiting at its 20-s timeout. The examples were
`vcsel_laser`, `soi_waveguide_modes`, `gesi_eam`, `pn_phase_shifter` and `point_source_wave`.
On Release, `close_times.py` opens each of the 49 examples, solves it for 3 s, and times the
close:

| example | before | after |
|---|---|---|
| vcsel_laser | 17.26 s | 8.02 s |
| vcsel_modes | 17.10 s | 7.67 s |
| soi_waveguide_modes | 2.11 s | 0.45 s |
| gaas_eam_excitons | 1.35 s | 1.23 s |
| pn_phase_shifter | 1.48 s | 1.01 s |
| point_source_wave | 1.03 s | 1.12 s |
| gesi_eam | 0.65 s | 0.20 s |
| the other 42 | 0.11 s at most | 0.11 s at most |

Under the sanitizers, the VCSEL's close took 203 s after a 20-s solve. The cause was found by
sampling the solve. The resonator's eigenfrequency search (68c6656) never asked whether to
stop. Its 127,462 unknowns take about 6 s to factorize, then about 12 s for 69 products of the
Krylov-Schur search. A model's tab waits for its job as it closes, and so does `fem_stop`, so
both waited out the rest. The mode analysis asked only between frequencies. The quantum wells'
and the PDE's eigenvalue searches did not ask either.

**Fixed.**
- `largestEigenvalues()` takes a `stop`, asked before each product; asked to stop, it returns
  nothing found.
- The resonator asks before and after its factorization, and passes the question to the
  search.
- The mode analysis asks after its factorization and passes it to both of its searches.
- The quantum wells' two searches and the PDE's eigenvalues pass it too.
- `fem_stop`'s description names the new points.

Tests:
- `test_fem_waves searchesStopWhenAsked`:
  - the search stopped after 3 products: 3 done, nothing found;
  - never stopped: asked once per product;
  - a waveguide's mode analysis: asked exactly 2 + its products' times, and stopped at the
    1st, 2nd, 3rd, middle and last check, each "cancelled" and asked no more.
- `test_fem_resonator stopsWhenAsked`: the same for a cavity's resonator, asked 3 + its
  products' times, stopped at six of them.

Broken on purpose, all caught, each check alone (seven breaks).

**Not done, said.** The factorization itself cannot be stopped: Eigen's SparseLU has no way in.
A VCSEL's tab still takes up to 8 s to close in the middle of one (minutes under the
sanitizers). The tab could leave its job running and not wait. That needs the job to outlive the
document safely, also at exit. It was left: a job's thread running past `main` is worse than a
wait.

### F6. The HDF5 reader reads past a project's end, and a size overflows

Found by the second pair of Lumerical runs, on the build with F3 and F4 fixed. Both seeds
stopped on the same input:

```
QFATAL : TestFemLumerical::fuzz() ASSERT: "n <= d.size - pos" in file .../qbytearray.h, line 602
```

The input was a `.ldev` cut after nine bytes: the HDF5 signature and the superblock's version.
`Hdf5File::openData` read the next two bytes (offset and length sizes) past the end. A Debug
Qt asserts; a Release build reads beyond the array. Earlier in one run, UBSan reported (and
went on):

```
fem_hdf5.cpp:214:89: runtime error: signed integer overflow: 1152921504606846976 * 512 cannot be represented in type 'qint64'
```

An attribute claimed 2^60 values of 512 bytes. Its name and type sizes ran past the message,
so the bytes left (`available`) were negative. The check `count > available / size + 1` then
compared with a huge unsigned number and passed, and `count * size` overflowed. The overflow
came from `fits(at, bytes)`, which added `at + bytes`. A damaged offset near 2^63 overflowed
that addition too, so the reader went on into garbage. That input was found again by running
the same seed with UBSan halting: `tests/data/lumerical_damaged_dataspace.ldev`, a damaged
copy of `lumerical_heat.ldev`.

Found on the way, reading the reader (not reached by the fuzzer):
- an object header's size added to its start unchecked (the same overflow);
- a version 2 dataspace's fourth byte read when two were checked;
- a B-tree's depth, up to 65535, walked as as many nested calls;
- a fractal heap's rows, up to 65535, used as a shift count (undefined from 64);
- a heap whose blocks start at size 0, which is a division by zero;
- an indirect block that is its own child, which recurses without end.

**Fixed.**
- `fits()` compares without adding.
- A superblock must have its 12 bytes, else "its HDF5 superblock is cut short".
- A dataspace's values are counted against the file's bytes as they are multiplied: each
  value is a byte at least.
- An object header must fit the file.
- A dataspace message must have its 4 bytes.
- A B-tree deeper than 64 is not walked. A heap of more than 64 rows, or of size-0 blocks,
  is not read.
- An indirect block is followed 64 levels at most.

Tests (`damagedInputsAreRefused`):
- the nine bytes refused with that reason, by `Hdf5File` and by the import;
- the overflowing project read whole: every object's links, attributes and datasets, then the
  import, `lumericalMaterials()` and `lum::properties()`.

Broken on purpose:
- the superblock check removed: caught in Release (the reason differs) and under the
  sanitizers (an abort);
- `decode` and `fits` as before, together: a UBSan abort.

Either alone is not caught: each covers the other's case. The reading-only items are not
tested one by one.

## N. Minor

- **N1.** A Lumerical script with an endless loop (`while (1) { b = b + 1; }`, the fuzzer's)
  runs to the interpreter's budget of 20 million statements. It is then refused, "the script
  runs too long", after 3.0 to 3.8 s in Release and over two minutes under the sanitizers.
  Bounded as designed. A smaller budget would refuse real scripts sooner, so it was left.
- **N2.** The tool fuzzer reported five "hangs" in seeds 1612 and 1613. Each was a `wait_for`
  given a timeout of 320 to 700 s by the fuzzer itself. The tool takes up to 3600 s, and the
  fuzzer waited 90. The replay of seed 1612 gave the same two. Not a bug.
- **N3.** QtTest stops a test function after 300 s. The first dataset and import fuzz runs
  ended so ("Received a fatal error" at 300,007 ms): set `QTEST_FUNCTION_TIMEOUT` for longer
  runs. QtTest's cap of warnings also swallows a fuzzer's closing count: pass `-maxwarnings 0`.

## Reproducing

The fuzzers built into the tests run on any build. They are skipped unless their variable is
set:

```bash
export QT_QPA_PLATFORM=offscreen QTEST_FUNCTION_TIMEOUT=7200000 QUCS_FUZZ_OUT=/tmp/fuzz-out
QUCS_DATASET_FUZZ=1200 build-asan/qucs/tests/test_dataset fuzz -maxwarnings 0
QUCS_MARKDOWN_FUZZ=1200 build-asan/qucs/tests/test_markdown_doc fuzz -maxwarnings 0
QUCS_CHAT_FUZZ=900 build-asan/qucs/tests/test_claude_code fuzz -maxwarnings 0
QUCS_LUMERICAL_FUZZ=900 QUCS_LUMERICAL_FUZZ_SEED=31 build-asan/qucs/tests/test_fem_lumerical fuzz -maxwarnings 0
QUCS_IMPORT_FUZZ=1800 build-asan/qucs/tests/test_data_import fuzz -maxwarnings 0
```

Each takes a `..._SEED` too. Slow inputs and the current one go to `QUCS_FUZZ_OUT`. Under
the sanitizers, give `ASAN_OPTIONS=detect_leaks=0`, and `UBSAN_OPTIONS=halt_on_error=1` to
stop at the first report with its input still on disk. Give each its own HOME, settings, cache
and trash (`HOME`, `QUCS_SETTINGS_DIR`, `QUCS_CACHE_DIR`, `QUCS_TRASH_DIR`).

The scripts beside this report take `QUCS` (the app's binary) and `HUNT_RUNS` (a scratch
folder for the servers' workspaces, settings, HOME, cache and trash, and their logs):

```bash
export HUNT_RUNS=/tmp/qucs-hunt-runs QUCS="$PWD/build-asan/qucs/qucs-s.app/Contents/MacOS/qucs-s"
python3 docs/bug_hunts/2026-10-16-fuzz/fuzz_qfem.py 101 150       # models: F5
python3 docs/bug_hunts/2026-10-16-fuzz/fuzz_tools.py 1611 1500    # the tools
QUCS="$PWD/build/qucs/qucs-s.app/Contents/MacOS/qucs-s" python3 docs/bug_hunts/2026-10-16-fuzz/close_times.py 3   # F5's table
```

The other fuzzers:

```bash
python3 scripts/ci/fuzz-sch.py build-asan/qucs/qucs-s.app/Contents/MacOS/qucs-s qucs-s-26.1.1/examples out-sch --count 3000 --seed 1016 --timeout 120
python3 scripts/ci/fuzz-simout.py build-asan/qucs/tests/simout_harness <a work folder of simulated examples> out-simout --count 2000 --seed 1016 --timeout 120
QUCS_MONKEY_SEED=1016 QUCS_MONKEY_STEPS=3000 build-asan/qucs/tests/test_gui_monkey
```

(`fuzz-simout.py`'s work folder is what `scripts/ci/smoke-test.sh simulate` leaves.)

The fixes' breaks: `breaks.py [name ...]` undoes each fix in turn, builds the test it names in
`build/` (`BRK_BUILD=build-asan` for those marked so), runs it - it must fail - and puts the
source back. Rebuild afterwards.
