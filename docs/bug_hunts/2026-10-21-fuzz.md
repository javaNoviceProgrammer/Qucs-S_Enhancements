# Bug hunt: fuzzing everything, again

*21 October 2026 - Qucs-S 27.0.2, `8c36b43` (the Release build and the ASan/UBSan build of it).
The findings written up as they came. All fixed in the commit that adds this report, but N2's
flow on the GUI thread (said, not changed).*

The user's request: "Now let's run a robustness campaign with fuzz tests to see if we can spot
any crashes. Throw everything you have at our qucs." Every fuzzer of the hunt of 16 October ran
again, on what has come since (the semiconductor's physics, the process flows, the layout
viewer, mode profiles). Four are new: the expressions, the layouts, the mode profiles' `.mat`
reader, and models made from the node kinds themselves.

It ran in the foreground on macOS arm64 with ngspice 46. Each run had its own HOME, settings,
cache and trash in a scratch folder. The fuzzers:

## E. Expressions

The expressions' fuzzer is new. Its first trial stopped in 1.4 s; its first two 20-minute runs
in 467 and 507 s, a third in 465 s. Each finding below was fixed before the next runs.

### E1. Nested thousands deep, an expression overflows the stack

```
==90718==ERROR: AddressSanitizer: stack-overflow ... Parser::take(char const*) fem_expr.cpp:676
    #1 Parser::parseUnary() ... #2 Parser::parseMul() ... #3 Parser::parseAdd() ...
```

2,247 brackets. Each bracket, sign and power is a level of the parser's recursion: about seven
calls, 3.5 kB of a sanitized build's stack a level, so the main thread's 8 MB ran out there; a
solve's thread had 512 kB (E3). A sum is a tree as deep as it is long, and the tree is compiled,
and freed, by recursion. A model's expressions come from its file, whoever wrote it.

**Fixed.**
- The parser reads 100 levels of brackets, signs and powers at most: "the expression nests too
  deeply (more than 100 levels)".
- Each node knows its tree's height. One past 200 is refused: "the expression is too deep (more
  than 200 levels)". A sum of 199 terms is still read.
- A node refused for its height is passed on as the refusal everywhere one is made, a number's
  unit's too.

### E2. A function nested 18 deep is written out 2^18 times

A model's function is inlined where it is called. `sq(u) = u*u + 1` reads its argument twice,
so `sq(sq(...sq(x)...))` 18 deep is 2^18 copies of `x`: 33 s under the sanitizers, a hang to
the user, and memory without bound a level further.

**Fixed.** The compiler counts its nodes: past 50,000 it stops, "the expression grows too large
with its functions written out (more than 50000 terms)". Four deep is still compiled and
evaluated (677 from 1).

### E3. A solve on a worker thread overflows its 512 kB

The models' fuzzer stopped six times in its first 21 models, each at `fem_solve` (`pn_diode`,
`si_inversion_valleys`, `diode_reverse_recovery` twice, `gesi_eam`, `fowler_nordheim_oxide`),
whatever was changed in them. A model is solved on a thread of its own, and macOS gives a
thread 512 kB of stack, a sixteenth of the main thread's. The material library's expressions
are compiled by recursion on the first solve. Under the sanitizers that overflowed it. The
tests solve on the main thread, so they never saw it.

Found while fixing it: every pool of `std::thread`s in the multiphysics code has the same
512 kB - the assembly's, the results', the mode analyses' frequencies, the rays' -, and one of
them runs whole solves: a sweep's points solved at once, each parsing and compiling its
expressions there.

**Fixed.**
- The model's job thread, the layout viewer's reading thread and the tools' layout thread have
  8 MB stacks (`QThread::setStackSize`).
- The pools are `detail::Threads` (`fem_problem.h`): `QThread`s of 8 MB, started at once, all
  waited for.

### E4. A table read at no number reads past its end

```
==91908==ERROR: AddressSanitizer: heap-buffer-overflow ... Expression::Table::at(double) const fem_expr.cpp:1598
    #1 Expression::eval(double const*) const fem_expr.cpp:1423
```

A material's property can be a table of the temperature. A diverged solve's temperature is not
a number. `upper_bound` with a NaN key gives the end, every comparison false, and the
interpolation read the element after it. Two runs stopped on it. A table of two arguments did
the same, and a table with fewer values than abscissae read past its values.

**Fixed.** Both `Table::at`s give NaN for NaN, and for a table short of values.

### E5. A unit's power wraps at 8 bits

```
fem_expr.cpp:52:67: runtime error: signed integer overflow: 2 * 2147483647 cannot be represented in type 'int'
    #0 Dim::pow(int) const  #1 UnitParser::power()
```

A dimension's powers are `int8_t`s. `m^2147483647` multiplied out was undefined. Within
range, it was silently wrong: `m^100 * m^100` is m^-56, `(1[m^3])^63` m^-67.

**Fixed.**
- A unit's power is a whole number below 64, as the expression's `^` already required: "a power
  in the unit must be less than 64".
- Products, quotients and powers of dimensions are held at ±127, not wrapped. No unit has such
  powers, and one held there is plainly wrong.

### N1. A sum of 65 terms was refused as functions calling each other

Found writing E1's test. The compiler's depth limit, 64, counted every level of the tree, and
its message was about functions: "the functions call each other too deeply" for `1+1+...+1`,
65 terms. Before E1 a sum of any length reached it.

**Fixed.** The compiler takes 256 levels, functions written out: "the expression is too deep
with its functions written out (more than 256 levels)". The functions' calls within each other
are counted apart, 64 at most, with the old message: a function calling itself still says so.

Tests (`test_fem_engine hostileExpressions`):
- 2,247 brackets, signs and powers refused, each "nests too deeply"; 99 of each read (1, -1, 1).
- A sum of 5,000 terms refused, "the expression is too deep (more than 200 levels)"; of 199,
  199.
- `sq` 18 deep refused, "too large", within 10 s; 4 deep 677.
- A function calling itself refused, "call each other too deeply"; 60 calls round a sum of
  130 terms (read 191 high, written out 311) refused, "too deep with its functions written
  out".
- A table read at NaN through an expression, NaN; at 1.5, 25. A table short of values, NaN. A
  table of two at (NaN, 1) and (1, NaN), NaN; at (2, 1), 26.
- `m^2147483647`, `m^99999999999`, `m^64` and `m^-64` refused; `m^63` read. Dimensions of
  m^100 times m^100, m^-100 over m^100, (m^3)^63 and (m^-2)^2147483647 held at ±127.
  `2[m^999]` refused, "less than 64".

`test_fem_physics aSweepsPointsAtOnceCompileDeepExpressions` (E3): a bar's conductivity of a
sum of 190 terms, swept over two lengths, two points at once - G as σ w/L at each. Under the
sanitizers, on threads of 512 kB, it overflows.

## L. Layouts

The layouts' fuzzer is new: GDSII and OASIS through the viewer's reader, drawing and search,
gdstk's readers below them (vendored, `third_party/gdstk`, patched by the hunt of the viewer's
day).

### L1. A chain of cells 3,000 deep overflows the stack

```
==93947==ERROR: AddressSanitizer: stack-overflow ... QList<int>::append(int)
    #4 qucs_s::layout::search(...)::$_0::operator()(int, ...) ... #11 search(...)::$_0 ... #12 search(...)::$_0
```

Its trial stopped in 4.8 s on the fuzzer's own deep file: 3,000 cells, each placing the next.
Search went down the hierarchy by recursion, a level a call, as deep as it was asked, and so did
drawing: the file decides how deep. The cells' bounds were found the same way (`finish`), deep
when a file lists its cells from the top down (the leaf last).

**Fixed.**
- Drawing and search go 256 levels down at most, whatever they are asked; deeper cells are drawn
  as frames, as cells past the depth asked always were.
- The bounds are found on a stack of their own (`finish`, a loop over a `std::vector`).

### L2. An OASIS text's property named by a number crashes the reader

```
==94728==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000 ... _platform_strlen
    #1 gdstk::copy_string(char const*, unsigned long long*) utils.cpp:60
    #2 gdstk::properties_copy(gdstk::Property const*) property.cpp:144
    #3 gdstk::read_oas(...)::$_0::operator()() const library.cpp:1610
```

OASIS refers to names by number, and gdstk keeps the number in the name's pointer until the
file's END. The viewer's patch of gdstk (`b1aa6cc`) resolves them all at once, at END or wherever
the file ends. It copied each text's properties from the text strings' table first, and resolved
the properties' names after. A property named by number 0 was copied as a null string.

**Fixed.** `resolve()` looks up the properties' names and values first (`third_party/gdstk`,
marked `Qucs-S`, and in its `README.qucs.md`).

### L3. An OASIS property of 2^62 values takes all memory

```
==94727==ERROR: AddressSanitizer: out of memory: allocator is trying to allocate 0x20 bytes
    #1 gdstk::allocate_clear(unsigned long long) allocator.hpp:33
    #2 gdstk::read_oas(char const*, double, double, gdstk::ErrorCode*) library.cpp:2514
```

A PROPERTY record gives its count of values, 15 or more as a number after it. gdstk made that
many, one at a time, each read from a file long ended: nine minutes, then the allocator gave up.
Counts of strings, points and repetitions were checked against the bytes left by the viewer's
patch; this one was missed.

**Fixed.** A property's count is checked the same way (`oasis_count_fits`): more values than
bytes left, the file is damaged, and what was read before it is shown with "It ends early or is
damaged".

Tests (`test_layout_doc`):
- `aHierarchyThousandsDeepIsReadAndDrawn`: a chain of 20,000 cells as GDSII and as OASIS, listed
  from the top down, read on a thread of 512 kB (as the viewer's reading thread was before E3);
  the top's depth 20,000 and its bounds (10000, 10000, 1, 1) µm; drawn and counted; searched
  from the top, nothing (the leaf is 20,000 levels down), from `C200`, the leaf's one square.
- `anOasisTextsPropertyNamedByNumberIsRead`: OASIS written by hand - a text string, a property
  of it named PROPNAME 0 (there is none), a cell, a text of that string -: read, the text "A",
  its property named "?".
- `anOasisPropertysCountPastTheFileIsSaidDamaged`: a cell, then a property of 2^62 values, in 40
  bytes: read within 10 s, the cell there, "damaged" said first.

## G. Geometry and mesh

### G1. A point 10^15 units off overflows the vertex hashes

```
fem_geometry.cpp:1234:47: runtime error: signed integer overflow: 9223372036854775807 + 1 cannot be represented in type 'long long'
```

The models' fuzzer set the shipped `boron_implant_anneal`'s silicon at `1e9[m]` in its model of
micrometres. The Form Union and the mesher find a vertex's neighbours by hashing it into cells
of their tolerance. `std::llround` of a cell's number past a `long long`'s range gives the
largest, and the neighbour's cell, one more, overflowed.

**Fixed.** A cell's number is clamped to ±4·10^18 (and not a number is 0) in both.

### G2. An object far off loses the others, silently or in the triangulation's words

Found writing G1's test. The Form Union's tolerance is 10^-6 of the whole geometry's extent. An
object a long way off makes every other object small beside it: thinner than the tolerance,
it was merged away, its vertices one, and what was left meshed as if nothing had happened. At
1e300 the rectangle's own width was lost in its coordinates' digits, and the union failed with
the triangulation's message, "Duplicate vertex detected: #1 is a duplicate of #4294967295".

**Fixed.** A solid object thinner than twice the tolerance is named: "si: thinner than the
union's tolerance, 8e-07 um (1e-06 of the geometry's extent, 0.8 um), lost to it - a position
far off, or a smaller tolerance (Form Union's)" - as the union's warning, or as its error in the
triangulation's place. No shipped example says it.

### M1. A mesh's largest element of 1e308 casts past an int

```
fem_mesh.cpp:283:32: runtime error: -1.01e+308 is outside the range of representable values of type 'int'
```

The models' fuzzer set the shipped `ge_photodiode`'s mesh `hmax` to 1e308. The mesher measures
narrow regions by rays from the boundaries, as far as the largest element; a grid of the
segments finds what each ray passes. Its cells' numbers were cast to `int`, then clamped: a ray
1e308 long was cast first.

**Fixed.** Clamped as doubles, then cast; not a number, the first cell.

Test (`test_fem_engine hostilePositions`): the shipped implant's silicon at `1e9[m]`,
`-1e9[m]`, `1e300`, `-1e300`, `1e15` and `0/0`: built and meshed, or refused and said; at
±1e300, "si: thinner than the union's tolerance"; the implant meshed with an `hmax` of 1e308.
Under the sanitizers, two positions (a build of the implant is 18 s there).

## P. Mode profiles

### P1. A UTF-32 text's character past 16 bits is cast

```
fem_modeprofile.cpp:340:93: runtime error: 6.42262e+06 is outside the range of representable values of type 'char16_t'
```

A `.mat` file's text (a profile's `about`) may be UTF-32. Each character was cast to `char16_t`:
undefined past 16 bits, and a real character there, an emoji, was cut to another.

**Fixed.** A character past 16 bits is UTF-16's two (`QChar::fromUcs4`); past Unicode's last,
the replacement character.

Test (`test_fem_modeoverlap aUtf32AboutIsRead`): a profile written by `profilesMat`, then an
`about` in miUTF32 after it - "A", U+1F600, 0x110000 -: its label "A😀�".

## PF. Process flows

### PF1. A flow narrower than a column reads its grid at row -1

The kinds' fuzzer's flow was 10^-6 µm wide with cells of 2.5 nm, and intermixed through openings
past its width. The dopants' grid had no rows, and refining it read row -1.

**Fixed.** A grid of no columns or no rows is not refined. The flow now stops with an ordinary
error (intermixing needs III-V compounds).

### PF2. A dopants' grid has no budget

The kinds' fuzzer's flow: rows of 0.1 nm, its depth 100 µm, a 2 µm substrate annealed an hour,
then filled to 300 µm. Opening it did not end in 120 s. Its grid would be 400 columns of
20,001 rows - 8 million cells, minutes for the anneal -, then 3 million rows more for the fill:
10^9 cells. A flow runs whenever the geometry is built (N2), so such a model could not be
opened.

**Fixed.** A grid of more than 5 million cells is refused, as it is made, as rows are added above
a new top (a deposit, a fill, an oxide's growth) and as an etch's fine rows are made deeper:
"its dopants' grid would have 8e+06 cells (400 across, 20001 down), more than 5e+06: a coarser dx
or dy, or less depth". The tests' largest is 805,200. A flow at 4.2 million cells anneals an
hour of boron in about five minutes in Release - slow, but asked for.

Test (`test_fem_process hostileFlows`): the narrow flow run or refused, said; the hour's anneal at
0.1 nm refused with that count, the fill to 300 µm of a flow 0.1 µm wide at 1 nm refused - all
within a minute (0.8 s; 17 s under the sanitizers).

## X. Counts read from a model

### X1. A count of 2^31 takes memory without end

The kinds' fuzzer's diode had a trap distribution of 2,147,483,647 levels. Its solve set up
for 30 s, then closing the model waited past 120 s; in Release it held 11.4 GB after five
minutes, still setting up. Each level is made at every node of the traps' boundary.

The other counts a model gives were read for the same: most are clamped (a mesh's, a sweep's
points at once, the modes, the states, the rays), and a 1D PDE's elements are bounded by its
line's 400,000. One more was not: a Floquet scan's kF points, each a solve, all listed first.

**Fixed.** Refused, said:
- a trap distribution's levels from 1 to 1000 (none or fewer was taken as one: refused too);
- a Floquet scan's points an even number from 2 to 1000.

Tests: `test_fem_devices trapLevelsAreBounded` (2147483647, 1001 and 0 levels in the MOS
capacitor's traps) and `test_fem_waves aScansPointsAreBounded` (2147483646, 1002 and 0 points),
each refused with its range; `test_fem_pde aLinesElementsAreBounded`, the line's own bound kept
(2147483647 elements refused, 50 solved).

## N. Minor

- **N2.** A process flow is run whenever the geometry is built, on the GUI thread: on opening a
  model, and 120 ms after a change of its parameters or geometry (not of its physics, mesh or
  studies). An hour's predeposition of boron at 1000 °C on a window of 1 by 2 µm at the default
  grid took 18.5 s to open in Release, the window frozen meanwhile; 45 s at rows of 1 nm. Nine
  of the kinds' fuzzer's plausible flows (implants, anneals and oxidations of 30 minutes,
  epitaxies, etches, on windows of 4 and 10 µm at columns of 10 and 20 nm) took 5.7 to 71 s to
  open in Release - past 120 s under the sanitizers, their nine findings. And `fem_build` built
  the geometry again whatever had changed: the flow run a second time (6.2 and 18.7 s for two of
  them), the mesh made stale.

  **Changed:** `fem_build` takes the geometry as it is when nothing has changed since it was
  built (`MultiphysicsDoc::currentGeometry`). Test (`test_multiphysics_doc
  aBuiltGeometryIsNotBuiltAgain`): a flow's model meshed by `fem_build`, then its geometry built
  by it: the mesh still current. **Not changed:** the flow on the GUI thread. It would move to
  the job thread, or its result be kept between builds keyed on all it reads (the flow, the
  materials and the library, the parameters, the model's folder, a layout's file) - a change of
  its own. PF2's budget bounds it.
- **N3.** Two of the models' fuzzer's closes took 46 and 66 s, after a mode analysis left
  solving at its 20-s timeout. Under the sanitizers one LU factorization of a waveguide takes
  that long, and it cannot be stopped (the hunt of 16 October, F5: "Eigen's SparseLU has no way
  in"). In Release the same close took 0.0 and 0.1 s.
- **N4.** The schematics fuzzer's one finding was a render killed by signal 9 with an empty log.
  Run alone, that mutant was refused in 0.8 s ("Wrong 'component' line format!"), 311 MB under
  the sanitizers. A dozen sanitized processes ran at once: the machine's memory.
- **N5.** Found reading what a flow reads, for N2. Its intermixing takes a III-V's composition
  (`compound`, `x`, `y`) from the model's materials. A model's materials are part of its
  physics: changing them made the solutions old, not the geometry. A flow's composition and
  dopants stayed as they were until the geometry or a parameter changed. **Fixed:** with a
  process flow in the geometry, a change of the materials builds it again; without one, as
  before. Test (`aBuiltGeometryIsNotBuiltAgain`, above): a material's `x` set by `fem_edit` -
  the flow's model built again (another topology after 400 ms), a rectangle's not.

## Reproducing

The fuzzers built into the tests run on any build, skipped unless their variable is set:

```bash
export QT_QPA_PLATFORM=offscreen QTEST_FUNCTION_TIMEOUT=7200000 QUCS_FUZZ_OUT=/tmp/fuzz-out ASAN_OPTIONS=detect_leaks=0 UBSAN_OPTIONS=halt_on_error=1
QUCS_EXPR_FUZZ=1200 QUCS_EXPR_FUZZ_SEED=25 build-asan/qucs/tests/test_fem_engine fuzz -maxwarnings 0
QUCS_PROFILE_FUZZ=900 QUCS_PROFILE_FUZZ_SEED=22 build-asan/qucs/tests/test_fem_modeoverlap fuzz -maxwarnings 0
QUCS_LAYOUT_FUZZ=1200 QUCS_LAYOUT_FUZZ_SEED=23 build-asan/qucs/tests/test_layout_doc fuzz -maxwarnings 0
QUCS_KINDS_DUMP=/tmp/kinds.json build-asan/qucs/tests/test_fem_engine dumpKinds
```

The others of the hunt of 16 October as it gives them (datasets, Markdown, chat images,
Lumerical, data import, schematics, simulator output, the monkey). `infuzz.sh` (beside this
report) runs one of the tests' fuzzers with its own HOME, settings, cache, trash and output.

The scripts take `QUCS` (the app's binary; the ASan build's by default for the repro scripts)
and `HUNT_RUNS` (a scratch folder):

```bash
export HUNT_RUNS=/tmp/qucs-hunt QUCS="$PWD/build-asan/qucs/qucs-s.app/Contents/MacOS/qucs-s"
KINDS_JSON=/tmp/kinds.json python3 docs/bug_hunts/2026-10-21-fuzz/fuzz_kinds.py semi 61 200
KINDS_JSON=/tmp/kinds.json python3 docs/bug_hunts/2026-10-21-fuzz/fuzz_kinds.py process 71 300
python3 docs/bug_hunts/2026-10-16-fuzz/fuzz_qfem.py 2105 300
python3 docs/bug_hunts/2026-10-16-fuzz/fuzz_tools.py 2113 1500
python3 docs/bug_hunts/2026-10-21-fuzz/repro_model.py <a finding>/model.qfem
python3 docs/bug_hunts/2026-10-21-fuzz/repro_close.py <a finding>/mutant.qfem 20
python3 docs/bug_hunts/2026-10-21-fuzz/breaks.py [name ...]
```
