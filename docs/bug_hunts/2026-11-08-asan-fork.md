# Bug hunt: the git killed by signal 9 under ASan

*8 November 2026 - `test_git_integration` on the macOS ASan/UBSan build, failing a different check
in about half its runs, found while checking the fix of the layout tab's crash
([2026-11-07-layout-close-crash.md](2026-11-07-layout-close-crash.md)). The user: "Do this task here:
'Find what SIGKILLs git in test_git_integration'". Fixed in the commit that adds this report.*

## Summary

| | Finding | Since | Fixed |
|---|---|---|---|
| **K1** | A program Qucs-S starts on the macOS ASan build (a git, a python) dies of signal 9 now and then, before it runs: `QProcess::Crashed`, exit 9, nothing written. `test_git_integration` fails one check or another; so, more rarely, do `test_claude_fuzz`, `test_claude_code` and the Python tests | the ASan build on macOS | no allocation stacks kept on macOS's ASan builds (`malloc_context_size=0`) |
| **K2** | The fix of 14 October (`736c82a`, eight frames of stack) rested on a mistake: that a child's stacks, stored at the first fork, are found by the next ones | `736c82a` | its explanation corrected with K1 |

Release builds and Linux never had it.

## What kills the git

Not Qucs-S's code. With a `kill()` interposer logging every SIGKILL and SIGTERM the test sends, and
its backtrace, the git that died (pid 77892) was in none of them: the test's three kills that run
were a `Job::cancel` and two `PythonDoc::stopCheck`s, all of their own processes. The
`ConsoleProcess` of the Terminal dock (`processconsole.cpp`), the one code that kills by pid, never
started in this suite.

macOS's crash reports name it, one for each dead git (15 of `test_git_integration`, 9 of
`test_claude_fuzz`, 3 of `test_python_doc`, 3 of `test_claude_code`, 1 each of `test_python_tools`
and `test_python_extras`, all on the ASan build): "crashed on child side of fork pre-exec", "BUG IN
CLIENT OF LIBPLATFORM: os_unfair_lock is corrupt".


The child is still the test, between `fork()` and the exec of git. macOS's fork handlers (here
libnotify's) allocate in the child. Under ASan that goes through the sanitizer's allocator, which
stores the allocation's stack in its depot and takes the depot's lock. The sanitizer does not hold
that lock across `fork()` on macOS (Apple clang 21): if another thread was storing a stack at the fork
(the thread pool's git, a file model's gatherer), the child inherits the lock held by a thread it does
not have, and libplatform kills it. On Linux nothing allocates in the child; in Release the system's
allocator locks itself across `fork()`.

## K2: why eight frames were not enough

`736c82a` (14 October) kept eight frames of each allocation's stack, so that every fork's stacks
would be the same, stored at the first fork and found after it without the lock. They are the same,
but a child stores into its own copy of the depot, which is gone when it execs git. The parent never
runs the fork handlers, so it never holds those stacks, and every child stores them again, taking the
locks. Eight frames made it rarer (fewer new stacks in the parent, so its threads hold the lock less),
no more.

## The fix

`tests/sanitizer_options.cpp`, linked into every test of the core and into the application:
`__asan_default_options` gives `malloc_context_size=0` on macOS's ASan builds. With no stack kept,
the allocator stores nothing in the depot, and the child takes no lock. A report keeps its access's
stack, but not where the memory was allocated or freed: `ASAN_OPTIONS=malloc_context_size=30`
overrides it for those (on a run that need not start processes, or on Linux). Linux and Release are
as they were. Chosen by the user over the six affected tests alone, and over leaving it.

Not done: starting git through `posix_spawn`, which runs nothing in the child. It would replace
`QProcess` for every program Qucs-S starts, to avoid a fault of a test build.

## How it was proved

[stress.py](2026-11-08-asan-fork/stress.py) runs a test in three copies side by side, three rounds,
in ctest's environment. It counts the runs that failed, the programs killed and macOS's new reports
of a child dead in `fork()`. On `test_git_integration`:

| `malloc_context_size` | runs failed | children dead in `fork()` |
|---|---|---|
| 8 (`STRESS_CONTEXT=8`, as since 14 October) | 4 of 9 | 9 |
| 0 (the build's, now) | 0 of 9 | 0 |

The same 3×3 before the change, with only `ASAN_OPTIONS` setting 0, also passed 9 of 9.

Through ctest on the ASan build, the six tests with such reports pass: `test_git_integration`,
`test_claude_fuzz`, `test_claude_code`, `test_python_doc`, `test_python_tools`, `test_python_extras`.

There is no test that fails every time without the fix: the death needs a fork at the moment another
thread holds the depot's lock. `stress.py` is the check, as `breaks.py` is for the hunts before.

Not verified: Linux's ASan build (unchanged), Qt 6.10.3.
