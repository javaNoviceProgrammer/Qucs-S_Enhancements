# Bug hunt: stress — random use of the main window, and schematics far beyond the usual size

*24 September 2026 — Qucs-S 26.1.2, `53bbb26`.*

Three kinds of stress, all against an ASan/UBSan Debug build unless said
otherwise:

1. **A GUI monkey**, `qucs/tests/test_gui_monkey`: a seeded random walk
   over copies of the ngspice examples - clicks, drags (some interrupted by
   an undo or a delete), double clicks, the wheel and keys in every mouse
   mode, the menu and toolbar commands, tabs, symbol view, hierarchy,
   component placement, closing and reopening - with every dialog that
   comes up cancelled or filled with odd values and accepted. A watchdog
   turns a step that never ends into an abort with the main thread's
   stack. 780 walks of 1,500 to 2,000 steps in all.
2. **A scale suite** of generated schematics, through the command line
   (`-n` netlist, `-p` render) on the Release build: chains of 1,000 to
   32,000 resistors, wire meshes up to 160x160, waveforms of 5 million
   points in every diagram type, sweep families of 20,000 curves, 400
   diagrams, 400-deep and self-including hierarchies, 8,000 wires with one
   label, 4,000 components on one spot, 5,000 equations, property values of
   10 MB, a text of 100,000 lines; and a transient of a million points
   simulated by ngspice and converted.
3. **The fuzzers** again (`scripts/ci/fuzz-sch.py`, `fuzz-simout.py`), with
   new seeds, and the simulator-output fuzzer on the output of a real
   NgSweep run (`ngsweep::datasetBlocks` had never been fuzzed).

*Status:* everything that crashed, hung or ran out of memory was fixed in
`53bbb26` (section C; `qucs/tests/test_stress_findings` has a test for each).
**A**, every edit and every load of a large schematic costing time
quadratic in its size, was fixed in `46332a5` (A4-A6). **B**, the wire
healer's invariants failing after some edits, is open.

## A. Fixed in `46332a5`: a large schematic froze on every edit, and loaded slowly

A1-A3 are the finding as it was written up; A4-A6 the fix.

### A1. Measurements

Release build, Apple M-series. A chain of resistors in rows of 100, joined
by wires (generator under *Reproducing*); "rotate" is Rotate on one selected
resistor, "undo" undoes it.

| components | wires | nodes | load | rotate one resistor | undo |
|---:|---:|---:|---:|---:|---:|
| 1,004 | 1,018 | 2,020 | 38 ms | 36 ms | 25 ms |
| 4,004 | 4,078 | 8,080 | 257 ms | 506 ms | 216 ms |
| 16,004 | 16,318 | 32,320 | 3.0 s | **8.9 s** | 2.7 s |

Load and netlist from the command line (`qucs-s -n`): 8,000 components
0.8 s, 16,000 2.7 s, 32,000 13.4 s. Four times the components take 7 to 17
times as long, the factor rising toward 16 as the quadratic part takes
over. Every edit that heals the schematic
costs like the rotate: moving or dragging (with the mouse or the cursor
keys), rotating, mirroring, aligning, distributing, setting on grid. Undo
and redo rebuild the whole document through the loader
(`Schematic::undo()` → `rebuild()` → `loadComponents()`), so they cost a
load.

For scale: the largest shipped example has 94 components and 203 wires
(the median, 33 elements), so no example comes near. It matters for
schematics generated or imported from a netlist, and for big designs:
from a few thousand components on, an edit lags visibly, and at 16,000 the
window stops for nine seconds after each one.

### A2. Where the time goes

**Loading** (`sample` of the 32,000-component load): 81% in
`Node::isOverlapping()`, called by `Schematic::findNode()`
(`schematic_element.cpp:345`), and 15% in `Schematic::provideNode()`
(`:356`) itself. For every pin (`simpleInsertComponent()`,
`schematic_file.cpp:834`) and wire end (`simpleInsertWire()`, `:882`),
`provideNode()` looks for a node at that position by comparing it with
every node of the document, and when it makes a new one, checks every wire
for one the node would split. N insertions × N nodes.

**Editing** (`sample` of the 16,000-component rotate): an edit heals the
whole document, not the part it touched (`Schematic::heal()`, `:2782`).

- 53%: `internal::mergeOverlappingNodes()` → `sameloc_nodes()` (`:419`),
  which compares every node with every other to find nodes that share a
  position.
- 31%: `invariants::noSamePlaceNodes()` (`:119`), the same all-pairs
  comparison, checked at the end of every heal (`:2901`). `QUCS_ASSERT`
  evaluates its condition in Release builds too - it logs instead of
  aborting - so every user pays for this check.
- Most of the rest: the all-nodes × all-wires loops - heal's "node above
  wire" step and `invariants::noNodesOnWires()` (`:146`, also asserted at
  the end of each heal).

### A3. Proposed fix, in order of payoff and risk

1. `sameloc_nodes()`: group the nodes by position in one pass over a hash
   map (`QPoint` → nodes). Same result, local change, about half of every
   edit's time.
2. The invariants that cost more than the edit - `noSamePlaceNodes`,
   `noNodesOnWires`, `noDuplicateWires` - checked in Debug builds only (a
   `QUCS_ASSERT_EXPENSIVE` that compiles out under `NDEBUG`), or rewritten
   with the same hash map. About a third.
3. Loading: a position → node map for the duration of a load or rebuild,
   which nothing moves nodes during, consulted by `findNode()`; the wire
   check in `provideNode()` against a grid of the wires' bounding boxes,
   or done once after the load.
4. Longer term: heal only around what an edit touched (the healer's plan
   already works node by node), and keep a spatial index of nodes in the
   `Schematic` for good. That needs every node move to go through the
   schematic; today `Node::moveCenterTo()` is called directly from wires,
   components and the healer.

By the profile's shares, 1 and 2 alone would take the 16,000-component
rotate from about nine seconds to about one and a half (an estimate, not
measured).

### A4. The fix

Items 1-3 of A3 - with every check still made in Release - and the other
edits that went through a list once per element. Item 4 was not needed.

- **Loading** (and so undo and redo, which rebuild through the loader):
  while the loader inserts the components or the wires of a document,
  `Schematic::IndexedInsertion` keeps a `qucs_s::InsertionIndex`
  (`conductor_index.h`): the nodes in a hash by place, for `findNode()`,
  and the wires filed under the 128 × 128 cells their bounding box covers,
  for the wires a new node may split. Loading only adds, so the index stays
  right; it goes with the section. Same schematic as before, element for
  element (checked below).
- **Healing** (`Schematic::heal()`): `sameloc_nodes()` groups nodes by place
  in one pass. The "node above wire" step asks, for each wire, which nodes
  lie on it (`qucs_s::NodesByPlace`: the nodes sorted by row and by column,
  a binary search for a horizontal or vertical wire, the narrower of the two
  bands for a diagonal one), and cuts a horizontal or vertical wire at all
  of them at once. The invariant checks use the same lookups and cost
  N log N; they still run in every build. `optimizeWires()` merges in one
  pass rather than looking for the first redundant node again after every
  merge. The healer's run of node replacements (`provideNode()` for each)
  uses the insertion index; the plan puts them together, and nothing moves
  or deletes in between.
- **Deleting**: the wires heal deletes (no length, duplicate, shorting a
  component) and what Delete takes go out of the document's lists in one
  pass (`deleteWires()`, `deleteComps()`), not one list search each; a node
  lets go of all its doomed wires at once.
- **Dragging**: decoupling a selection takes the nodes it leaves with
  nothing connected out of the list in one pass - and frees them, which it
  never did (a leak on every drag).
- **Pasting**: each pasted component looked through every component's name
  (making two string copies each) for the next free number; a paste keeps a
  table of the numbers in use by name prefix now (`Schematic::BulkNaming`).
  A new name counts for every prefix in the table, as it would in a look
  through the components, so the names come out as before.

### A6. Found on the way

- **A subcircuit pin numbered in the billions hung the load** (a monkey
  walk; fixed in `46332a5`). The walk typed 2147483647 into a subcircuit
  Port's number and saved; the symbol then says `.PortSym -10 60 2147483647
  0 -1`. `Component::analyseLine()` makes a pin for every number up to the
  highest (16.7 million after the coordinate clamp), and
  `Subcircuit::createSymbol()` took the unused ones out one at a time, each
  removal moving the rest of the list: opening the parent schematic never
  finished. A number below 1 read `Ports.at(-1)`. Pin numbers above 100,000
  or below 1 now make the symbol invalid, and the instance gets the
  standard symbol with a pin for each Port (`test_stress_findings`); unused
  pins go in one pass and are freed (they leaked), in `SpiceLibComp` too.
- **Healing depended on where the nodes were in memory** (fixed in
  `62b04d4`). Run twice through the same Release binary, the 26 edits
  ended in a different state for 640 of the 651 schematics; the first
  difference came at an edit of part of the selection or at aligning or
  distributing everything. Orders came from addresses, which macOS lays out
  differently on each run: the healer (`qucs_s::Healer`) went through the
  nodes in the order of a `std::map<Node*, ...>` and sorted its plan by
  priority with an unstable sort, and decoupling a dragged selection merged
  its new nodes in the order of an `unordered_set<Node*>`, which picks the
  node - and so the wire and label - that stays. Where repairs interact, the
  order decides. The healer now goes through the nodes by place (nodes on
  one place in the order first met) and keeps that order within a priority;
  decoupling merges in the order the nodes were made; distributing sorts
  stably (the order `std::sort` gives equals differs between standard
  libraries). The 26 edits now end the same for all 651 in two runs, and in
  one process as in ten. `test_stress_findings` loads a schematic twice,
  the second time into a scrambled heap, and requires the same edits to
  end the same; it failed three runs out of three before. (Under ASan the
  monkey's walks replayed even before: seed 3061 reached the same hang at
  the same step twice.)
- **A pasted component kept the document it was parsed in** (a monkey walk
  on the ordered healing, seed 3216; fixed in `62b04d4`). A paste is parsed
  by the document current when it begins, and each component takes that
  document as its schematic (`Component::containingSchematic`, through
  which a subcircuit finds its file). Dropped into another document, it
  kept the first - freed when that one closed, and read by the next
  recreate of the subcircuit: Save All renumbering ports crashed. A
  component inserted into a schematic takes it as its own now
  (`insertComponent()`, `insertRawComponent()`, the loader).
- **Close All freed the property editor** (seed 3227; fixed in `62b04d4`).
  Editing a property on the canvas puts `QucsApp::editText` into the
  document's viewport. Closing one document takes it out first; Close All
  and Close all left / right / but current deleted the documents without,
  the editor went with the canvas, and the next use of `editText` read
  freed memory. They take it out (and let go of the mouse's elements) as
  closing one does. Each has a test (`test_stress_findings`, `test_panes`)
  that fails without the fix.
- **A misplaced node went to the wrong port** (read in the code; fixed
  with `aMisplacedNodeMovesToTheClosestPort`). When a node sits at none of
  its ports' places, healing moves it to the closest, but
  `findClosest()` never lowered its best distance: the last place closer
  than the first won. The 26 edits of the 651 schematics never met the
  case (their results are the same with the fix).
- **Zooming out on a schematic with far-away elements overflowed the
  canvas** (seed 6019, which walked the Claude Code dock too; not
  reproducible on a rerun, the walk depends on the fake claude's timing).
  The model plane is the union of everything in the schematic, and a file
  or a dialog can put an element anywhere an int reaches; the canvas was
  the plane's size times the scale, cast to int: 7·10⁹ pixels, then
  Q3ScrollView's `-x + visibleWidth()` and `dy * 5` overflowed and Qt's
  checked `QRect::width()` aborted. A file's `<View=...>` went straight
  into the plane and the scale (any corners, a scale of 0 or `nan`). The
  model plane now stays within `Schematic::ModelLimit` (2²³ units) of the
  origin - `renderModel()` cuts the plane and its focus point, the used
  area is cut corner by corner without computing a width, a loaded view
  is cut and its scale made a number in [0.1, 10] - so the canvas is at
  most 1.7·10⁸ pixels at the largest zoom; `modelToContents()` maps a
  point beyond it in double. Elements further away than 8 million units
  are not scrolled to. `farAwayElementsDoNotOverflowTheCanvas` loads
  elements at ±2·10⁹ with five hostile views and zooms, scrolls, shows
  all, the selection and no zoom; with the limit at 2³⁰ it overflows
  under UBSan. 96 ASan seeds after the fix: no sanitizer report at all.

## B. Open: the wire healer's invariants fail after some edits

`Schematic::heal()` checks its invariants when it starts and when it
finishes. `QUCS_ASSERT`
aborts a Debug build; a Release build logs `Invariant violated: ...` and
carries on. Two of them fail.

### B1. A node inside a diagonal wire's tolerance band, not connected to it (`noNodesOnWires`)

In 6 of the monkey's walks, after Rotate (5) or Distribute horizontally
(1) on the current selection, the check at `schematic_element.cpp:2903`
found a node lying "on" a diagonal wire that had not been split there
(three of them logged with coordinates):

| node | wire | wire length | distance from the line | band half-width there |
|---|---|---:|---:|---:|
| (740, 290) | (960, 200) – (480, 400) | 520 | 1.52 | 1.61 |
| (1410, 380) | (960, 730) – (1450, 350) | 620 | 0.78 | 0.96 |
| (2700, −360) | (2670, 430) – (2710, −570) | 1,001 | 1.60 | 1.82 |

What "on" means (`qucs_s::geom::is_between()`,
`geometry/multi_point.h:109`): on a horizontal or vertical wire, exactly
on it; on a diagonal wire, |MA| + |MB| − |AB| ≤ 0.01. That is an ellipse
around the wire whose half-width at M is √(2 · 0.01 · |MA| · |MB| / |AB|),
so it grows with the wire's length: about 0.7 units at the middle of a
100-unit wire, 1.6 at the middle of a 520-unit one. Every node in the
table is inside its band.

`heal()` does have a step that splits a wire at every node the predicate
puts on it, and the final check uses the same predicate. So something
after that step must put the node inside a band. The likely candidate,
not traced step by step: `optimizeWires()`, near the end of `heal()`,
merges two collinear diagonal segments into one longer wire, and the
longer wire's band is wider where they met. A node 1.5 units off the
middle of a 520-unit wire lies near the ends of its two 260-unit halves,
where their bands narrow to nothing, so the split step leaves it alone;
once the halves are merged it is inside the whole wire's band (1.61
units there).

**Not reproducible with whole-selection edits on the examples alone.**
Every shipped schematic (251) was given each of rotate, mirror X, mirror Y,
align left, align top, center, distribute horizontally and vertically
(2,008 edits), and a chain of 12 such edits: no violation. That fits:
not one shipped example has a diagonal wire, and B1 needs one. The walks
made theirs along the way (dragging, placing, and the healer's own
connecting wires) before the edit that tripped the check.

**Effect.** In Release, a node (a pin or a wire end) within a unit or two
of a diagonal wire stays unconnected, although the drawing shows it on the
wire; the check only logs.

**Proposed fix.** Make "on the wire" exact for diagonals. Node
coordinates are integers, so M is on AB exactly when the cross product
(B − A) × (M − A) is 0 (in 64-bit arithmetic) and M is inside the
bounding box. Use it in both the healer's step and the check. This
changes what counts as touching a diagonal wire everywhere `is_between()`
is used (`provideNode()`'s split too): a node one unit off a diagonal
would no longer be taken as on it, so check it against the examples. A
narrower alternative: run the "node above wire" step again after
`optimizeWires()`, until nothing changes.

### B2. Labelled nodes with nothing connected (`noOrphanNodes`)

Deterministic: open `examples/xyce/Xyce_Examples/09-Lorenz/lorenz.sch`,
Select All, Rotate (or make any other edit that heals). A Debug build aborts
at the check at the start of `heal()` (`schematic_element.cpp:2785`,
`n->conn_count() > 0` at `:114`); a Release build logs it once for each of
ten nodes.

The cause: the example's SpLib components name their library files by
absolute paths on the author's machine
(`/users/russo/.qucs/user_lib/LT1057.lib`, `.../AD633_JT.lib`). The files
ship in the example's `user_lib/` folder. `misc::properAbsFileName()`
falls back to the bare file name next to the schematic and in the project,
not `user_lib/`, so the components load without pins. The ten labels
`V_P15` / `V_M15` were saved on their supply pins (as zero-length wires),
and they end up on nodes that nothing connects to.
`templates_ngspice/AC_TRAN_Active_Filter_analysis.sch` does the same
(`Vcc` / `Vee` on OP1 and OP2) whenever the SpiceOpamp library is not
found. The walks also met this check after deletes, once after a delete in
the middle of a drag, which the harness can do and a user cannot.

**Effect.** In Release the check logs and nothing else changes: the
labels are drawn, and nothing connects to them because nothing is there. A
Debug build aborts on the first edit of such a schematic.

**Proposed fix.** A node that carries a label is not an orphan: accept it
in the invariant (or have the loader drop a label that nothing connects
to, with a warning). And give the example the relative path
`user_lib/LT1057.lib` (and `user_lib/AD633_JT.lib`), which does resolve
next to the schematic.

## Reproducing

The monkey, one walk or many (a seed replays the same walk on every
platform, as long as the code is the same - a change anywhere changes
where the walk goes after it):

```bash
QT_QPA_PLATFORM=offscreen QUCS_MONKEY_SEED=1007 QUCS_MONKEY_STEPS=2000 build-asan/qucs/tests/test_gui_monkey
seq 1 100 | xargs -P 10 -I{} sh -c 'QT_QPA_PLATFORM=offscreen QUCS_MONKEY_SEED={} QUCS_MONKEY_STEPS=2000 build-asan/qucs/tests/test_gui_monkey > /tmp/monkey-{}.log 2>&1 || echo "seed {} failed"'
```

At `53bbb26`, seed 1007 stops on B1 at step 1250 (Rotate), and seed 1050
stops on B2 at step 190.

The chain of A (N resistors in rows of 100, joined by wires, a source and
a DC simulation):

```python
import sys
n = int(sys.argv[1])
R = '  <R R{} 1 {} {} -26 15 0 0 "1k" 1 "26.85" 0 "0.0" 0 "0.0" 0 "26.85" 0 "european" 0>\n'
comps = ['  <Vdc V1 1 -60 60 18 -26 0 1 "5 V" 1>\n', '  <GND * 1 -60 90 0 0 0 0>\n',
         '  <.DC DC1 1 200 -200 0 40 0 0 "26.85" 0 "0.001" 0 "1 pA" 0 "1 uV" 0 "no" 0 "150" 0 "no" 0 "none" 0 "CroutLU" 0>\n']
wires = ['  <-60 30 70 30 "" 0 0 0 "">\n']
for k in range(n):
    row, col = divmod(k, 100)
    x, y = 100 + 100 * col, 30 + 100 * row
    comps.append(R.format(k + 1, x, y))
    if col < 99 and k < n - 1:
        wires.append(f'  <{x + 30} {y} {x + 70} {y} "" 0 0 0 "">\n')
    elif k < n - 1:
        wires += [f'  <{x + 30} {y} {x + 30} {y + 50} "" 0 0 0 "">\n',
                  f'  <70 {y + 50} {x + 30} {y + 50} "" 0 0 0 "">\n',
                  f'  <70 {y + 50} 70 {y + 100} "" 0 0 0 "">\n']
print(f'<Qucs Schematic 26.1.2>\n<Properties>\n  <View=0,0,2000,2000,1,0,0>\n  <Grid=10,10,1>\n</Properties>\n'
      f'<Symbol>\n</Symbol>\n<Components>\n{"".join(comps)}</Components>\n<Wires>\n{"".join(wires)}</Wires>\n'
      '<Diagrams>\n</Diagrams>\n<Paintings>\n</Paintings>')
```

```bash
python3 chain.py 16000 > chain_16000.sch
time QT_QPA_PLATFORM=offscreen build/qucs/qucs-s.app/Contents/MacOS/qucs-s -n --ngspice -i chain_16000.sch -o /dev/null
```

The edit times of A1 came from a throwaway QtTest that loads the chain,
selects one resistor, calls `Schematic::rotateElements()` and `undo()` under
a `QElapsedTimer`. The profiles came from `sample <pid>` during the same
runs. `qucs/tests/test_large_schematics` builds the same chain (in rows of
100) and times the edits of A5 at 2,000 and 8,000 components.
